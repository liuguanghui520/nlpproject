第 6 页：模型的三种“不知道” 环节一 · 课程导入 ① 知识边界 问：某冷门领域的某个细节规定？ 训练语料里 根本没有 这条信息。 模型只能用一个「最像的已知事实」去补——结果就是编造。 ② 时效 问：上个月新发布的那份文件怎么规定的？ 参数里的知识 停在训练截止点 ，之后发生的事一概不知。 这是纯静态模型的固有局限。 ③ 私有数据 问：我们公司去年的差旅报销标准是多少？ 这是 内部文档 ，公网语料里不存在。 而它恰恰是业务系统里问得最多的一类问题。 三类问题的共同点 答案 都存在于某个可访问的文本里 ——只是不在模型参数里。既然如此，与其想办法把知识“塞进”模型（昂贵、滞后、不可追溯），不如 在需要时把相关文本找出来放进上下文 。这就是检索增强生成（RAG）的核心思想。 另一条线：模型不仅要答得对，还要答得起—— 推理成本决定了这套方案能不能规模化上线 。 东北大学软件学院 · 自然语言处理 06
第 7 页：两条路线：把知识放进参数，还是放在外部 环节一 · 课程导入 · 考点 维度 放进参数（继续预训练 / 微调） 放在外部（RAG / 工具调用） 成本 极高（数据 + 算力） 低 （建索引 + 检索） 时效 滞后，更新要重新训练 改文档即生效 ，分钟级 可审计 无法追溯一句话来自哪份材料 可给引用 ，逐条核对来源 注入大量新事实 困难——小数据微调主要用于调整行为，不是灌知识 只要库里有就能用 推理开销 训练一次性投入大；推理时模型可能更小更快 需额外检索 + 更长上下文（延迟与费用上升） 擅长 行为、格式、风格、领域口径的稳定化 事实性知识与可溯源回答 本讲的判断（也是工程上的标准答案） 不是二选一，而是分工： 知识（事实、政策、内部文档）走 RAG；行为（格式、语气、拒答边界、领域口径）走微调。 先用 RAG 把知识问题解决，再用微调把行为对齐 ——顺序反了会浪费大量标注成本。 东北大学软件学院 · 自然语言处理 07

第 9 页：推理的两个阶段：prefill 与 decode（考点） 环节二 · 知识点讲解 · 考点 ① Prefill（预填充） 输入：整段提示（如 2000 token） → 一次性送进模型， 并行 计算每个位置 → 把每层的 K / V 缓存下来 计算密集 ：时间随输入长度增长 但可以高度并行，GPU 利用率高 输出：第一个 token 的概率分布 + KV 缓存 ② Decode（解码） 每步只处理 一个新 token → 但要读取全部历史 KV 缓存 → 输出下一个 token，循环 显存带宽密集 ：算力大量闲置 生成 500 个 token 就要跑 500 次 所以“首 token 延迟”与“每 token 延迟”要分开看 为什么必须区分这两个阶段 因为它们的 瓶颈完全不同 ：prefill 吃算力、decode 吃显存带宽。所以优化手段也不一样—— 批处理与算力优化帮 prefill，KV Cache 管理、量化与投机解码帮 decode 。不区分两阶段，讨论“推理优化”就会变成一堆名词的堆砌。 两个必背指标： TTFT（首 token 延迟，主要受 prefill 影响） 与 TPOT（每 token 延迟，主要受 decode 影响） 。 东北大学软件学院 · 自然语言处理 09
第 10 页：KV Cache：拿显存换计算 环节二 · 知识点讲解 · 考点 不缓存：每步重算历史 生成第 t 个 token 时： 需要前面所有位置的 K、V → 不做缓存，就要把 1..t−1 全部重算一遍 → 计算量随长度 平方级 增长 生成 500 token ≈ 做 500 次长度递增的前向 有缓存：只算新 token 缓存 K、V 后： 每步只算新 token 的 Q / K / V 历史 K / V 直接从缓存读取 → 每步计算量降到与新 token 同量级 代价：缓存要保存 每一层 × 每个头 × 每个位置 的 K 和 V 这笔交易的实质 用显存换计算。 在长输出时极其划算（省下的计算量是平方级的），但它把 显存变成了真正的瓶颈 ——而显存有限，直接限制了三件事：能支持的 并发请求数 、能支持的 上下文长度 、能用的 批大小 。 所以工业界的核心问题变成： 如何把 KV Cache 管得更省、更碎、更能共享 ——这就是下一页 PagedAttention 要解决的。 东北大学软件学院 · 自然语言处理 10
第 11 页：KV Cache 的显存账（考点） 环节二 · 知识点讲解 · 考点 KV Cache 大小 = 2 （K 与 V）× 层数 × 头数 × 每头维度 × 序列长度 × 批大小 × 每元素字节数 配置 计算 结果 说明 层 32 · 头 32 · d_k 128 · L 4096 · batch 1 · FP16 2 × 32 × 32 × 128 × 4096 × 1 × 2 B ≈ 2.1 GB 单条请求已经不小 同上，batch = 8 × 8 ≈ 17 GB 与模型权重同量级 同上，batch = 16 × 16 ≈ 34 GB 单卡开始吃紧 同上，L 32768 · batch 4 2 × 32 × 32 × 128 × 32768 × 4 × 2 B ≈ 68 GB 长上下文 + 并发极其昂贵 三个直接结论 缓存与 序列长度 成正比 → 上下文越长越贵 缓存与 批大小 成正比 → 并发越高越贵 两者相乘 → 长上下文与高并发是一对矛盾 对应的三种省显存手段 ① 量化 KV Cache （FP16 → INT8/INT4，直接减半或再减半）。 ② 分页管理 （PagedAttention，减少碎片与浪费）。 ③ 共享与复用 （同一前缀的请求共享缓存，如系统提示缓存）。 一个工程判断 当你看到“支持 128K 上下文”时，要追问： 在多大并发下、用多少张卡、延迟是多少？ 上下文长度是 能力上限 ，并发与延迟是 成本现实 ——必须一起看。 东北大学软件学院 · 自然语言处理 11
第 12 页：PagedAttention 与 vLLM（考点） 环节二 · 知识点讲解 · 考点 传统实现的两个碎片问题 内部碎片 ：每个请求按“最大可能长度”预留连续显存，实际用不到那么多——剩下的就是浪费。 外部碎片 ：不同请求之间留下无法利用的空洞。 实测浪费可达 60%–80% ——这是吞吐上不去的直接原因。 PagedAttention：借操作系统分页思想 把 KV Cache 切成固定大小的「块」 块可以存在 不连续 的物理显存里 再用一张 块表 记录逻辑顺序 逻辑： [块0][块1][块2][块3] 物理： 块7 → 块2 → 块13 → 块5 ← 不要求连续 三个收益 碎片浪费从 60%–80% 降到 4% 以下 显存利用率提升 → 并发吞吐显著提升 支持 前缀共享 ：多个请求共享相同前缀的块（如同一个系统提示） 工程位置 vLLM 就是基于 PagedAttention 的推理引擎，是目前服务端部署的主流选择之一；同类还有 SGLang 等。 它们的共同点： 把“显存管理”当成一等公民 ，而不是把模型跑起来就完事。 一条可迁移的方法论 PagedAttention 的创新不在数学，而在 系统设计 ——它把一个“算法问题”重构成“内存管理问题”，借用了操作系统里成熟几十年的方案。 这是软件工程背景的同学最该带走的一种思路。 东北大学软件学院 · 自然语言处理 12
第 13 页：量化：为什么可以把精度降下来 环节二 · 知识点讲解 · 考点 基本思路：把连续的浮点取值映射到少数几个离散档位 FP16 → INT8 ： 65536 档 → 256 档 FP16 → INT4 ： 65536 档 → 16 档 量化： x_q = round( x / s ) s 为缩放因子 反量化： x ≈ s · x_q 显存： FP16 = 2 字节 / 参数 → INT8 = 1 字节 → INT4 = 0.5 字节 为什么质量损失可以接受 神经网络的权重与激活值 对精度并不敏感 ——大量权重集中在很小的数值范围内，微小的量化误差在多层累加后并不显著放大。 实践证明：INT8 通常几乎无损；INT4 在合理方案下质量损失也很小。 为什么量化能加速 decode 阶段是 显存带宽密集 ——瓶颈在于把权重从显存搬到计算单元。 权重变小 4 倍 → 搬运量少 4 倍 → 直接加速解码 。这也是量化在推理侧比训练侧更常见的原因。 代价与前提 需要一批 校准数据 来确定每层合适的缩放因子；不同层数值分布差别很大，粗暴地用同一个 s 会明显掉点。 量化后的模型在小众任务或长链推理上的退化可能更明显—— 必须自己评测 。 东北大学软件学院 · 自然语言处理 13
第 14 页：量化方案对比（考点） 环节二 · 知识点讲解 · 考点 方案 量化对象 核心思想 特点 GPTQ （2022） 权重（3–4 bit） 逐层后训练量化，用 二阶信息 （Hessian 近似）补偿量化误差 INT4 权重量化的经典方案；实现成熟 AWQ （2023） 权重（4 bit） 观察到只有 少量重要通道 影响大，对这些通道做保护（按激活幅度缩放） 比 GPTQ 更稳、更快 ，当前主流之一 SmoothQuant （2022） 激活值 + 权重（W8A8） 用等价变换把激活的量化难度“迁移”一部分到权重：W·X = (W/s)·(s·X) 让 激活也能 INT8 ，进一步提升吞吐 NF4 （QLoRA） 权重（4 bit） 针对 正态分布 数据设计的信息论最优 4 位格式 配合 LoRA 在单卡微调大模型（第 13 讲） KV Cache 量化 缓存的 K / V 对缓存单独量化（FP16 → INT8/INT4） 缓解长上下文与高并发的显存压力（第 11 页） 必须分清的一条线： 权重量化 （GPTQ / AWQ / NF4）主要省显存、加速权重搬运； 激活量化 （SmoothQuant）才真正提升矩阵乘吞吐。两者可以叠加。 东北大学软件学院 · 自然语言处理 14
第 15 页：蒸馏、剪枝与 MoE：三种不同的省法 环节二 · 知识点讲解 · 概念层 ① 知识蒸馏 让小模型（学生）模仿大模型（教师）的 输出分布 ，而不只是硬标签——软标签携带“哪些类容易混”的信息。 L = α·CE( p_s , p_t ) + (1−α)·CE( p_s , y ) 代表作 DistilBERT ：参数 −40%、速度 +60%、保留约 97% 效果。 ② 剪枝 非结构化剪枝 ：把不重要的单个权重置零——压缩率高，但需专门硬件才能加速。 结构化剪枝 ：整行、整列、整个注意力头删掉—— 才能真正加速 ，工程上更实用。 典型流程：训练 → 按重要性打分 → 剪掉一批 → 再微调恢复。 ③ 稀疏与 MoE 混合专家（MoE）：把 FFN 换成多个专家（FFN 占每层参数约 2/3），每个 token 只激活其中一两个。 参数量暴涨，计算量基本不变 ——把“参数量”与“算力”解耦。 代价：总显存占用大（要装下所有专家）、路由负载均衡是难点。 一句话区分三者 蒸馏 是把能力搬进小模型； 剪枝 是删掉冗余结构； MoE 是把参数量与计算量解耦。 前两者为省资源，后者为在有限算力下扩参数。 东北大学软件学院 · 自然语言处理 15
第 16 页：投机解码：用小模型加速大模型（考点） 环节二 · 知识点讲解 · 考点 ① 草稿模型（小而快）连续猜出 k 个 token 猜测： 大 学 位 于 沈 ② 大模型一次前向， 并行验证 这 k 个位置（k+1 个位置一次算完） 验证： 大✓ 学✓ 位✓ 于✓ 沈✗ → 用大模型的结果替换“沈” ③ 接受前 4 个 token，多产出 4 个 → 相当于大模型只跑了 1 次前向 最关键的性质：不改变输出 在正确的接受/拒绝规则下，投机解码 数学上与直接用大模型采样等价 ——它是保持分布的无偏加速。 这意味着它 不牺牲质量 ，只要草稿猜得准就能白拿加速——与量化（有损）形成对比。 加速比取决于什么 取决于草稿模型与目标模型的 一致率 ：猜得越准，一次接受越多，加速越大（典型 2–3 倍）。 如果草稿模型太差、接受率低，反而增加额外开销。 三种草稿来源 独立小模型 （同系列的小尺寸版本） 同模型的浅层 / 多头 （自投机） 检索式草稿 （从文档里复制片段作为候选） 与量化对比记忆： 量化是“有损换资源”，投机解码是“无损换并行” ——两者可以叠加使用。 东北大学软件学院 · 自然语言处理 16
第 17 页：部署形态与成本测算（考点） 环节二 · 知识点讲解 · 考点 三种部署形态 API 调用 ：零运维、按量付费；数据出域、单价高、有限流 云上自建 GPU ：可控、可微调；需运维与容量规划，闲时浪费 本地 / 端侧 ：数据不出域、隐私最好；性能与模型规模受限 三件常用工具 vLLM ：服务端高吞吐推理引擎（PagedAttention + 连续批处理），适合线上服务。 Ollama ：本地一键跑模型，适合开发、演示与个人使用。 llama.cpp ：CPU / 端侧友好，支持多种量化格式，适合无 GPU 场景。 成本测算四问 ① 每次请求输入 + 输出多少 token？ ② 每天多少次调用？ ③ API 单价 × 总 token 量 = 多少？ ④ 自建：GPU 小时单价 × 卡数 × 利用率折算 = 多少？ 结论 ：低并发、需求不稳定 → API 更划算；高并发、稳定负载 → 自建更划算。 一个必须算进去的隐藏成本 自建的成本不只是 GPU 租金：还有 运维人力、模型更新与评测、容灾与扩容、闲时资源浪费 。很多团队算完才发现，在中低负载下 API 反而更便宜—— 先算账，再选型。 东北大学软件学院 · 自然语言处理 17

第 19 页：RAG 全链路：六步走完（考点） 环节二 · 知识点讲解 · 考点 ① 加载 PDF/网页/DB → 文本 → ② 切块 长文档 → 片段 → ③ 向量化 片段 → 向量 → ④ 存储 向量库 + 元数据 用户问题 query → ⑤ 检索 ANN + 关键词 + 重排 → top-k 片段 → ⑥ 生成 拼进提示 · 只依据资料 · 给引用 → 答案 + 来源 可核查 哪一步决定上限 ② 切块 ：切得不好，再好的嵌入也检索不到。 ③ 嵌入 ：模型选错，语义相近的片段就排不上来。 ⑤ 检索 ：召回不到正确片段，后面全是无米之炊。 哪一步决定体验 ⑥ 生成 ：即使检索对了，模型也可能不用资料而凭记忆作答，或加了资料里没有的内容。 所以要在提示里写死三条约束（第 26 页），并做引用校验。 一句话记住 RAG 的定位 RAG 不是“让模型变聪明”，而是 把模型从“知识源”降级为“阅读理解器” ——它只需要理解给定材料并作答，而不需要记住事实。 这个角色转换，是它比微调更可靠、更可控的根本原因。 东北大学软件学院 · 自然语言处理 19
第 20 页：为什么 RAG 有效：对着幻觉四层成因看 环节二 · 知识点讲解 · 考点 幻觉成因（第 14 讲） RAG 能否解决 怎么解决 / 为什么不能 层 1 数据层 （语料里没有这条信息） 能 把正确文本放进上下文，模型不需要“回忆”，只需要“阅读” 层 3 知识截止 （训练之后的新事实） 能 改文档即生效——这是 RAG 相对微调最大的时效优势 层 2 训练目标层 （从不奖励真实、没学会拒答） 部分能 靠提示约束解决：“只依据资料作答”“资料未提及就说不知道”（第 26 页） 层 4 解码与交互层 （采样放大错误、提示被误导） 基本不能 要靠低温解码、外部验证与引用回查；RAG 本身不管这些 忠实性幻觉 （输出与给定资料不一致） 不能 RAG 改变的是“模型能看到什么”，不改变“模型是否严格依据资料” ——必须加引用校验与忠实度评估 这句判断请务必记住 RAG 缓解事实性幻觉（靠“查”），但缓解不了忠实性幻觉（要靠“管”）。 很多人以为“上了 RAG 就不会幻觉了”——恰恰相反，RAG 会引入一类新的失败： 模型给了引用，但引用并不支持它的结论 。这也是第 29 页评估指标里要单独测“忠实度”的原因。 东北大学软件学院 · 自然语言处理 20
第 21 页：切块策略：检索质量的第一道关卡（考点） 环节二 · 知识点讲解 · 考点 为什么必须切块 ① 嵌入模型有输入长度上限；② 检索粒度要匹配问题粒度——整篇文档作为一个向量会让语义被平均掉；③ 上下文预算有限，不能把整篇塞进去。 ① 固定长度切块 按 token 数机械切分（如每 500 token 一块）。 优点 ：简单、可预测、易并行。 缺点 ：可能从句子中间切断，破坏语义完整性。 适合格式规整的数据（日志、表格导出）。 ② 递归切块（最常用） 按层级依次尝试切分：先按段落切，太大就按句子切，再大就按词切，直到满足块大小。 尽量在自然边界切开 ，兼顾语义完整与长度控制。这是目前最常用的默认策略。 ③ 按语义切块 用嵌入相似度检测语义转折处——相邻句子相似度骤降的地方就是切点。 效果更好 （每块内部主题一致），但需要额外计算、成本更高，适合高质量要求的场景。 关键参数 ① 块大小 常用 200–800 token 。太小→上下文不足、检索碎片化；太大→语义被平均、检索不精准、上下文浪费。 关键参数 ② 重叠 相邻块之间保留 10%–20% 的重叠，防止关键信息正好落在切点上被割断。 关键参数 ③ 元数据 每块必须带上 来源、章节、页码、时间 ——用于元数据过滤（只看最新版）、引用标注与权限控制。 东北大学软件学院 · 自然语言处理 21
第 22 页：嵌入模型与相似度度量 环节二 · 知识点讲解 · 考点 ① 相似度度量 度量 特点 余弦相似度 只看方向，不受向量长度影响—— 最常用 内积 受长度影响；某些模型专门用内积训练 欧氏距离 看重绝对位置；与归一化后的内积等价 关键纪律 ：选择的度量必须与模型训练时使用的一致，否则排序会明显变差。 ② 模型选择要看任务 检索 （query→document）：常用双塔对比学习训练，是 RAG 的主力 语义相似度 ：句对相似判断，训练目标不同 聚类 / 分类 ：看重簇结构 重排 ：交叉编码器（把 query 与文档一起送进模型），精度更高但更慢 同一个模型在不同任务上的排名可能差别很大—— 不要只看一个任务的榜单 。 ③ 评测与领域适配 MTEB （大规模文本嵌入评测基准）覆盖多种任务与语言，可以用来做初筛——但它的分数不保证在你自己的数据上同样排序。 通用中文模型通常够用； 医学、金融等专业领域 可能需要领域微调或选领域模型。最可靠的做法： 在自己 100–500 条真实问题上对比几个候选模型 。 东北大学软件学院 · 自然语言处理 22
第 23 页：近似最近邻（ANN）：HNSW 与 IVF（考点） 环节二 · 知识点讲解 · 考点 为什么需要近似 如果有 100 万个向量 ，逐个算相似度（精确检索）每次查询要做 100 万次计算——延迟无法接受。 ANN 用少量精度换取巨大的速度提升。 ① HNSW：分层可导航小世界图 上层（稀疏）：长距离快速跳转 ●───● │ 中层： ●──●──● │ 底层（稠密）： ●─●─●─●─●─● ← 精细定位 查询：从顶层入口出发，逐层向下搜索 把查询复杂度从 O(n) 降到接近 O(log n) ；是目前最常用的向量索引。代价是内存占用较高、构建较慢。 ② IVF：倒排文件索引（先分簇再搜） 先用聚类把向量分到 K 个簇 查询时只在最相近的 nprobe 个簇里搜索 → 搜索范围缩小几十倍 nprobe 是关键参数 ：调大→更准但更慢；调小→更快但可能漏掉正确结果。 常与 乘积量化（PQ） 组合：把向量切段分别量化，进一步压缩内存——即经典的「IVF + PQ」。 三个必须知道的取舍 召回率 vs 延迟 （近似程度越高越快，但可能漏掉正确结果）； 内存 vs 精度 （量化压缩省内存但损失精度）； 构建成本 vs 查询成本 （HNSW 构建慢但查询快）。 没有免费的午餐——参数要在自己的数据与延迟要求上调。 东北大学软件学院 · 自然语言处理 23
第 24 页：向量数据库选型 环节二 · 知识点讲解 · 概念层 选择 定位 优势 局限 / 适用 Chroma 轻量嵌入式向量库 pip 装上就能用、零运维、API 简洁 规模与并发能力有限—— 适合原型与教学 Milvus 专业分布式向量数据库 多种索引（HNSW / IVF / PQ）、十亿级规模、水平扩展 运维复杂度较高——适合生产级大规模场景 pgvector PostgreSQL 扩展 向量与业务数据 在同一张表 ，支持事务与元数据过滤 十亿级性能不如专用库——适合已有 Postgres 技术栈 FAISS 向量检索 库 （不是数据库） 索引算法齐全、性能强、可嵌入 不提供持久化与服务能力，需自己封装 云托管服务 厂商托管的向量检索 零运维、弹性扩缩 成本较高、数据出域、供应商绑定 选型四问 ① 数据规模多大？ 万级以内用 Chroma 就够；千万级以上考虑 Milvus 或云服务。 ② 要不要和业务数据联查？ 要与订单、用户表做过滤与关联 → pgvector 最省事。 ③ 有没有运维能力？ 没有人运维就别自建分布式库。 ④ 要不要事务与权限？ 合规场景需要数据库级事务与细粒度权限。 一个务实的建议 先用最轻的方案把链路跑通，再做规模决策。 课程项目与原型阶段 Chroma 完全够用；等数据规模与并发真的上来，再迁移到 Milvus 或 pgvector—— 而迁移的成本主要在于重建索引，而不是改业务代码（前提是把向量层抽象好）。 东北大学软件学院 · 自然语言处理 24
第 25 页：混合检索与重排：召回要全，重排要准（考点） 环节二 · 知识点讲解 · 考点 单一检索的两种失败 向量检索 擅长语义相似，但对 精确匹配 很弱——查询某个产品编号、法条编号、人名时，经常召回一堆“语义相近但不对”的段落。 关键词检索（BM25） 字面精确，但对 同义改写 无能为力——用户说“报销标准”，文档里写“差旅费用上限”，就匹配不上。 混合检索 + RRF 融合 同时跑两路检索： 向量检索 → 排名 A1 A2 A3 … 关键词检索 → 排名 B1 B2 B3 … 用 RRF 融合（倒数排名融合）： score(文档 d) = Σ 每路 1 / ( k + rank 该路 (d) ) → 两路都排得靠前的文档胜出 重排（rerank）：召回之后再精挑 ① 召回：两路检索各取 top-50 → 合并去重（约 100 条） ② 重排：用 交叉编码器 把 query 与每条候选 一起 送进模型打分 ③ 取前 5–10 条 → 拼进上下文 为什么更准 ：交叉编码器能让 query 的每个词与文档的每个词直接交互，比“各自编码再算向量距离”精细得多。代价是慢——所以只用在少量候选上。 一句话记住分工 召回要快、要全；重排要准、可以慢。 这就是典型的“粗排 + 精排”漏斗结构——推荐系统里用了几十年的思路，在 RAG 里同样成立。 只做向量检索不做重排，是很多 RAG 系统效果上不去的直接原因。 东北大学软件学院 · 自然语言处理 25
第 26 页：生成阶段：让模型真的用上检索到的资料 环节二 · 知识点讲解 · 考点 提示模板（三条约束必须写死） 【资料】 [1] ……（片段一，带来源） [2] ……（片段二） [3] ……（片段三） 【问题】…… 【要求】 ① 只依据上面的资料作答 ，不要使用你自己的知识； ② 资料中没有提到的内容，必须回答「资料未提及」； ③ 每个结论后面标注来源编号，如 [1]。 为什么这三条有效 它们把模型从『凭记忆作答』切换到『 基于给定材料作答 』——角色从“知识源”变成“阅读理解器”。 第②条尤其关键： 显式允许它说“不知道” ，这是提示层最便宜也最有效的抗幻觉手段，而很多团队恰恰忘了写。 必须配套的三件事 引用校验 ：检查模型标注的编号是否真的支持该结论（字符串回查 + 语义判断） 上下文压缩 ：把片段裁剪到只保留相关句，减少噪声与 token 消耗 明确边界 ：为每段资料编号并标出来源，防止模型把不同来源的内容混在一起 一个常见误区 以为“把资料塞进上下文，模型就会用”。实际上模型很可能 混合使用 资料与自己的参数知识——尤其在资料与它“知道”的不一致时。 所以约束必须显式写、并且 可验证 （引用校验就是验证手段）。 东北大学软件学院 · 自然语言处理 26
第 27 页：RAG 的八种典型失败模式（考点） 环节二 · 知识点讲解 · 考点 失败模式 表现 修复手段 ① 切块切断了关键信息 答案横跨两个块，任何一块都不完整 加重叠、按语义切、把相邻块一起返回 ② 嵌入模型不适配 领域术语（药名、产品号）检索不到 换领域模型，或在自己数据上微调嵌入 ③ 只做向量检索 精确编号、人名、法条号匹配失败 加关键词检索 + RRF 融合（第 25 页） ④ top-k 太大或太小 太小漏掉证据；太大引入噪声、稀释注意力 召回多一点 + 重排 ，精挑 5–10 条进上下文 ⑤ 资料相关但模型不用 模型凭记忆作答，忽略给定资料 写死三条约束 + 引用校验（第 26 页） ⑥ 引用不支持结论 给了编号，但对应内容并不支撑该结论 引用回查 + 忠实度评估 （第 29 页） ⑦ 多跳问题单跳检索 需要先查 A 再据 A 查 B，一次检索拿不到 查询改写、查询分解、多轮迭代检索 ⑧ 缺权限与时效过滤 检索到用户无权查看的或已过期的版本 元数据过滤 （按部门、密级、生效日期） 排查顺序： 先看“正确的片段有没有被召回”（检索问题），再看“召回了模型有没有用”（生成问题） ——把这两类分开，定位速度会快很多。 东北大学软件学院 · 自然语言处理 27
第 28 页：RAG 进阶：五种提升方向（概念层） 环节二 · 知识点讲解 · 概念层 ① 查询改写（Query Rewriting） 用户的问题往往是口语化、带指代、缺上下文的。先让模型把它改写成 检索友好的查询 ：补全指代、加同义术语、生成多个查询变体再合并结果。 HyDE 思路 ：先让模型生成一个「假设答案」，再用假设答案去检索——因为答案与文档的用词分布更接近。 ② 多路召回 + 融合 向量检索、关键词检索、元数据过滤、知识图谱多路并行，再统一融合排序。 不同路线的失败模式不同， 多路并行能显著提高召回率 ——这是工程上最稳的一招。 ③ Self-RAG：把检索变成迭代 让模型自己决定： 要不要检索？检索结果够不够？要不要再检索一次？ 用反思标记训练模型输出这些决策，把一次性的“检索→生成”变成多轮迭代—— 解决多跳问题（失败模式⑦）的主要手段。 ④ GraphRAG：处理全局性问题 把文档抽成 实体与关系图 ，先在图上做社区发现与摘要，再回答问题。 它专门解决普通 RAG 的一个硬伤： “这个语料库的主要主题是什么？” ——这类问题需要全库视角，向量检索天然做不到。 ⑤ 上下文压缩（最容易被忽略、性价比很高） 召回片段往往只有一两句相关，其余是噪声。用一个小模型（或规则）把片段 裁剪到只保留相关句 ——既减少 token 成本，又提高模型的注意力集中度。 很多“模型不用资料”的问题，压掉噪声后就自然好了。 东北大学软件学院 · 自然语言处理 28
第 29 页：RAG 评估的四类核心指标（考点） 环节二 · 知识点讲解 · 考点 指标 评哪一段 问的问题 低分说明什么 上下文召回率 Context Recall 检索 该找到的资料，有没有被召回？ 切块、嵌入或检索策略有问题—— 这是 RAG 的上限 上下文精确率 Context Precision 检索 召回的片段里有多少真正相关？ 噪声太多，稀释了模型注意力——需要重排或压缩 忠实度 Faithfulness 生成 答案是否完全由检索到的上下文支持？有没有编造？ 模型没管住——需要写死约束 + 引用校验（ 检测忠实性幻觉的关键指标 ） 答案相关性 Answer Relevance 生成 答案是否切题、是否回答了用户的问题？ 提示设计或问题理解有问题（例如答非所问、绕圈子） 怎么用这四个数定位瓶颈 召回低 → 检索端问题（切块/嵌入/检索策略）。 召回高但忠实度低 → 生成端没管住（提示约束、引用校验）。 两者都好但相关性低 → 提示或问题理解有问题。 工程上的一个经验顺序 先把召回做上去，再优化生成。 因为召回是上限——召回不到的资料，再好的提示也变不出来。 而提升召回最有效的三步： 改切块 → 加关键词检索 → 加重排 。 与第 14 讲的衔接 这四个指标都可以用 AI 评委 来自动打分，但同样要面对 位置偏差、冗长偏差 等问题。 所以必须抽一批人工标注做校准——评测的方法论在第 14 讲已经给过了。 东北大学软件学院 · 自然语言处理 29
第 30 页：RAGAS 与评估实施四步 环节二 · 知识点讲解 · 考点 RAGAS：面向 RAG 的“无参考评估”框架 它不需要人工写标准答案，而是用模型来判断忠实度、答案相关性、上下文精确率与召回率等指标—— 把评估成本降到可以随迭代频率运行的量级 。 实施四步 ① 准备测试集 ：50–200 条真实问题，覆盖常见问题、边界问题与「资料里没有的问题」 ② 跑完整链路 ：记录每条问题召回的片段、最终答案、引用编号 ③ 自动打分 ：用 RAGAS 或自写的 AI 评委逐条算四类指标 ④ 人工校准 ：抽 30–50 条人工标注，统计评委与人的一致率 测试集设计的三个要点 ① 必须包含“资料里没有答案”的问题 ——这是检验模型会不会说『资料未提及』的唯一方式。很多 RAG 系统的幻觉率就是被这类问题暴露的。 ② 覆盖多跳问题 （需要跨文档组合信息）与 精确匹配问题 （编号、人名、日期）。 ③ 标注每条问题的“标准来源” ——用于计算上下文召回率。 把评估接进迭代循环 RAG 的参数很多（块大小、重叠、top-k、是否重排、提示模板），每改一处都应该跑一次评估。 没有评估，调参就是碰运气 ；有了这 50–200 条测试集与四个指标，每次改动都能立刻看出是变好还是变坏—— 这是 RAG 工程从“手工艺术”变成“可控工程”的分界线。 东北大学软件学院 · 自然语言处理 30
第 31 页：代码骨架：20 行搭出 mini-RAG 环节二 · 知识点讲解 · 可照抄 # 用 LlamaIndex 搭一个最小 RAG（CPU 可跑，也可换 LangChain） from llama_index.core import SimpleDirectoryReader, VectorStoreIndex from llama_index.core import Settings from llama_index.embeddings.huggingface import HuggingFaceEmbedding # ① 加载 + ② 切块（块大小与重叠是可调参数，别写死） Settings.chunk_size = 512 Settings.chunk_overlap = 64 docs = SimpleDirectoryReader("./data").load_data() # ③ 嵌入模型（中文场景选中文模型） Settings.embed_model = HuggingFaceEmbedding(model_name="BAAI/bge-small-zh-v1.5") # ④ 建索引并存储（默认内存，可换成 Chroma / Milvus / pgvector） index = VectorStoreIndex.from_documents(docs) # ⑤ 检索（top-k 可调） retriever = index.as_retriever(similarity_top_k=8) # ⑥ 生成：提示里写死三条约束（第 26 页） from llama_index.core.prompts import PromptTemplate qa = PromptTemplate("""资料：\n{context_str}\n问题：{query_str} 要求：① 只依据资料作答；② 资料未提及时回答"资料未提及"；③ 结论标注来源编号。""") engine = index.as_query_engine(text_qa_template=qa, retriever=retriever) print(engine.query("我们公司去年的差旅报销标准是多少？")) 工程要点： 把 chunk_size / overlap / top-k / 模型名 / 提示模板全部外置成配置 ——否则无法做参数对比实验，也就无法优化。 东北大学软件学院 · 自然语言处理 31

第 38 页：本讲小结 环节四 · 小结 1 推理优化 prefill 计算密集，decode 显存带宽密集 ——瓶颈不同，手段不同。 KV Cache 用显存换计算； PagedAttention 借操作系统分页把碎片从 60–80% 降到 4% 以下。 量化 分权重量化（GPTQ/AWQ/NF4）与激活量化（SmoothQuant）； 投机解码 无损加速； MoE 解耦参数量与算力。 2 RAG 链路 六步 ：加载 → 切块 → 向量化 → 存储 → 检索 → 生成。 召回是上限。 切块三策略（固定 / 递归 / 语义）+ 三参数（大小 / 重叠 / 元数据）；嵌入度量必须与训练一致；索引用 HNSW 或 IVF。 混合检索 + RRF + 重排 ：召回要快要全，重排要准可以慢。生成侧写死三条约束并做引用校验。 3 评估与落地 四类指标 ：上下文召回率 / 精确率（检索端）、忠实度 / 答案相关性（生成端）——分别定位两类问题。 测试集必须包含『 资料里没有答案 』的问题。 用 RAGAS 把评估接进迭代循环：没有评估，调参就是碰运气。 一句话带走 RAG 的本质不是“让模型更聪明”，而是 把模型从“知识源”降级为“阅读理解器” ——它只需要理解给定材料并作答，不需要记住事实。 这个角色转换，是它比微调更可靠、更可控、更便宜的根本原因。 复习索引： prefill/decode · KV Cache 显存账 · PagedAttention · GPTQ/AWQ/SmoothQuant · 投机解码 · MoE · RAG 六步 · 切块三策略 · HNSW/IVF · 混合检索与 RRF · 重排 · 八种失败模式 · 四类评估指标 。 东北大学软件学院 · 自然语言处理 39
