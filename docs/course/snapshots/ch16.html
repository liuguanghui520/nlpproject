共同的变化

模型获得了一个可以作用于外部世界的动作空间。它不再只是生成文本，而是能改变文件、发送请求、执行命令、下订单。

这正是 Agent 的本质——也是它风险的来源。

一句必须记住的对比

一次回答错了，用户可以不信、可以重问——错误的成本是零。

一次行动错了，可能已经转了钱、删了文件、发了邮件——成本可能不可撤销。

这条差别决定了本讲后半段的所有工程约束。

什么是 LLM 智能体：四个关键词环节二 · 知识点讲解 · 考点
定义

以语言模型为决策核心，在环境中通过调用工具采取行动、接收反馈、并根据反馈调整后续行动的自主系统。

四个关键词
  • 决策核心：模型负责判断“现在该做什么”
  • 动作空间：工具定义了它“能做什么”——动作空间就是能力边界，也是风险边界
  • 反馈闭环：行动结果（成功/失败/返回值）回注上下文，影响下一步
  • 自主性：能连续多步执行，而不是一问一答
与传统程序的关键差别
传统程序Agent
控制流由人写死由模型运行时决定
输入结构化参数自然语言 + 环境反馈
行为确定、可测试不确定、难以穷举测试
失败方式异常与错误码“看起来做完但没做对”
一句话理解：把“调用哪个函数、传什么参数、下一步做什么”交给模型决定——这就是 Agent 与普通程序最本质的区别。

四大组件：大脑、手脚、笔记本、管家环节二 · 知识点讲解 · 考点
①模型（大脑）

负责理解目标、拆解任务、决定下一步动作。

模型能力越强，Agent 上限越高，成本也越高。常见工程做法：用强模型做规划，用小模型做执行——既保质量又控成本。

②工具（手脚）

搜索、数据库、代码执行沙箱、业务 API、文件系统、邮件与工单系统。

工具的数量与描述质量直接影响模型能否选对——工具太多会混淆，描述不清会误用。动作空间就是风险边界。

③记忆（笔记本）

短期记忆：当前对话与中间结果，放在上下文里（受窗口限制，需要压缩与摘要）。

长期记忆：跨会话的知识沉淀，放在向量库里（第 15 讲）——例如用户偏好、历史结论、已办事项。

④规划（管家）

把大目标拆成可执行步骤，并在执行中根据反馈调整（可能需要重新规划、回溯或求助人工）。

规划的质量决定了 Agent 是“步步为营”还是“走一步看一步”。

重要提醒：四者不是并列的功能模块，而是互相依赖的闭环——工具返回值进记忆，记忆影响规划，规划决定下一次工具调用。

ReAct：思考与行动交替循环（考点）环节二 · 知识点讲解 · 考点
ReAct = Reasoning（推理） + Acting（行动） 循环： ┌─────────────────────────────────────────────┐ │ Thought 我现在需要做什么？还缺什么信息？ │ │ Action 调用某个工具，带上参数 │ │ Observation 工具返回的结果（可能失败！） │ │ → 回到 Thought，判断：信息够了吗？要换工具吗？ │ └─────────────────────────────────────────────┘ 终止条件：模型判断信息足够 或 达到最大步数上限
为什么必须交替

只推理不行动 → 凭记忆猜（幻觉）；只行动不推理 → 不知道该调什么、也不知道结果够不够。

交替循环让每一步都建立在真实反馈上，而不是模型对世界的想象上。

三个必须设计的约束
  • 最大步数：防止无限循环烧钱（常见 5–15 步）
  • 工具失败处理：返回错误时是重试、换工具还是放弃？必须显式约定
  • 全程记录：每步的 Thought/Action/Observation 都要落日志（第 24 页）
它的地位

ReAct 是今天几乎所有 Agent 框架的基础范式——LangChain 的 Agent、LlamaIndex 的 Agent、各家工具调用流程，本质上都是它的实现。

它的价值不在于“新”，而在于把一个模糊的“智能”变成了可工程化的循环结构。

Reflexion：把失败变成可复用的经验环节二 · 知识点讲解
① 尝试执行任务 → 失败（或结果不理想） ↓ ② 写反思：为什么失败？哪一步错了？下次应该改什么？ ↓ ③ 把反思存入记忆（作为可复用的经验） ↓ ④ 带着这段经验再试一次 → 仍然失败则继续反思（限制轮数）
价值在哪

它把『失败』变成了可复用的经验，避免在同一个坑里反复跌倒。

对于有明确成功判据的任务（代码跑测试、SQL 能查出结果、格式校验通过），这一层收益特别明显。

它的边界（与第 14 讲呼应）

反思的有效性取决于模型能否正确判断失败原因。

如果判断能力不足，反思可能得出错误结论，导致下一轮越改越偏——这与第 14 讲『自我反思在缺乏判断能力时无效甚至有害』是同一件事。

正确做法：把外部验证器（测试、校验、检索）的结果作为反思的依据，而不是让模型空想。

工程约束

必须限制反思轮数（常见 2–3 轮），否则会陷入“反思—重试—再反思”的死循环，既烧钱又无进展。

而且每一轮的反思内容都要落日志——它是排查 Agent 行为最有价值的材料。

Toolformer：让模型自己学会用工具环节二 · 知识点讲解 · 概念层
它要解决的问题

Agent 的一个基础难题是：『哪一步该用哪个工具』的训练信号从哪来？

人工标注成本极高；而如果只靠提示词教，模型在复杂任务上容易选错或该用不用。

做法：用“有没有帮助”当监督信号
① 让模型自己生成大量候选 API 调用 ② 逐个检查：加上这次调用之后， 模型预测后续文本的准确率是否提高？ ③ 只保留“确实有帮助”的调用作为训练数据 ④ 用这些数据微调模型

结果：模型学会在需要时调用计算器、问答、搜索、翻译、日历等 API，不需要人工标注“哪一步用哪个工具”。

为什么这篇工作值得在课上讲

它是“用可验证的信号训练模型行为”这一思路的早期代表——而这条思路后来在第 13 讲的 GRPO（用规则/验证器给奖励）与今天的推理模型训练里被推到了极致。共同点：只要能自动判断“结果好不好”，就能用强化学习或筛选的方式塑造模型行为。

记忆：短期在上下文，长期在库里环节二 · 知识点讲解 · 考点
短期记忆（放在上下文里）

内容包括：当前对话、中间结果、工具返回值、已执行步骤。

受上下文窗口限制，工程手段：滚动摘要（把旧的对话压缩成摘要）、关键信息抽取（只留结论与参数）、分层压缩（保留最近若干轮 + 摘要更早的）。

长期记忆（放在外部存储里）

跨会话沉淀：用户偏好、历史结论、已办事项、领域知识。

通常存在向量库里（第 15 讲），检索方式与 RAG 完全一致——所以长期记忆可以理解为“关于用户与历史的 RAG”。

设计要点 ① 写入什么

不是所有信息都值得记。要有筛选规则：只记长期有效、可复用、且未来会用到的信息（偏好、约束、结论），而不是全量对话流水。

设计要点 ② 何时召回

按相似度（与当前任务相关）、按时间（最近的优先）、按实体（与当前提到的客户/项目相关）——三种策略常组合使用。

设计要点 ③ 如何更新与遗忘

信息会过期（用户的偏好变了、政策更新了）。必须支持覆盖与删除，否则记忆里会积累错误，而且越用越错。

多智能体：角色分工与协作环节二 · 知识点讲解 · 考点
典型角色分工（以“开发一个小功能”为例） 产品经理：把模糊需求写成明确规格（输入、输出、边界） ↓ 架构师 ：选择技术方案、拆分模块、定义接口 ↓ 工程师 ：按接口写实现代码 ↓ 测试 ：写测试用例、跑测试、报告失败 ↓ 评审 ：检查是否符合规格与规范，决定是否通过
三种协作模式
  • 串行（流水线）：前一个角色的输出是后一个的输入
  • 并行：各自独立产出，再汇总与择优
  • 辩论：多个角色互相质疑，多轮后收敛
价值在哪

① 分工让每个角色的提示更聚焦、上下文更短、质量更稳——一个提示里塞太多目标反而都做不好。

② 互相检查能发现单智能体看不到的问题——类似人类团队的代码评审，独立视角本身就有价值。

风险：链条越长越危险

每个角色的输出都可能带一点错，而下游角色会把这些错当成事实继续加工——误差逐级放大。

所以多智能体不是“越多越好”：能用一个 Agent 加几个工具解决的，就不要拆成五个角色。

东北大学软件学院 · 自然语言处理15
级联幻觉：多智能体最致命的问题（考点）环节二 · 知识点讲解 · 考点
上游角色的一个错误，会被下游当作“既定事实”继续加工 架构师：调用 getUserOrdersV2() 接口 ← 这个接口其实不存在 ↓ 工程师：按这个接口名写了调用代码 ← 没有质疑，直接采用 ↓ 测试 ：编造了一个“该接口正常返回”的测试结果 ← 错误被进一步“合理化” ↓ 评审 ：看到有接口、有测试，判为通过 ← 验收通过 最终交付：一套完整、规范、但根本跑不起来的代码
为什么它会放大

因为下游角色信任上游输出——这在人类协作里是效率的来源，在模型协作里却成了风险的入口。

而且每一层都会“补全”细节，把不确定的东西写得越来越确定。

防御 ① 关键节点加外部验证

接口是否存在 → 查 API 文档；代码能否跑通 → 真跑测试；数据是否查得到 → 真查一次库。

把“相信上游”换成“验证上游”，这是唯一可靠的办法。

防御 ②③ 质疑机制与链条长度

② 让下游有打回机制：明确告诉它“上游输出可能有错，发现不合理要质疑并退回”，而不是无条件接受。

③ 限制链条长度与角色数量：每增加一个角色，就多一次误差放大机会。能合并就合并。

MCP：把“模型 ↔ 工具”的对接标准化（考点）环节二 · 知识点讲解 · 考点
它要解决的问题：N × M 的集成爆炸

有 N 个模型应用、M 个工具服务。如果两两定制对接，就要维护 N×M 套适配代码——每加一个工具就要改所有应用，每换一个模型就要改所有工具。

没有统一协议：N × M 套适配 有了统一协议：N + M 套实现 应用A ─┬─ 工具1 应用A ──┐ ┌── 工具1 ├─ 工具2 ├─ 协议 ─┤ 应用B ─┼─ 工具1 应用B ──┘ └── 工具2 └─ 工具2 双方都只实现协议本身
协议里的三个角色
  • 宿主应用 Host：用户直接使用的 AI 应用
  • 客户端 Client：宿主内部负责与服务器通信的组件
  • 服务器 Server：暴露能力的服务，提供工具、资源、提示模板三类能力
它带来的实际好处

工具一次实现、多处复用——同一个数据库工具可以在多个 AI 应用里直接用。

权限与审计可以集中管理——连接层统一做鉴权、限额与日志，比在提示词里约束可靠得多。

一句类比

MCP 对 Agent 工具生态的意义，类似于 USB 接口对硬件外设的意义：定义了统一的插口，设备与主机才不必两两定制。

⚠ 协议仍在演进，具体能力以官方最新文档为准。

A2A：智能体之间的协作协议（考点）环节二 · 知识点讲解 · 考点
它要解决什么问题

不同团队、不同框架构建的智能体，彼此不认识、不会协作——一个负责报销的 Agent 无法把任务交给负责审批的 Agent。

A2A 让它们能互相发现、互相委派任务、交换结果。

三个核心概念
  • 智能体卡片（Agent Card）：描述该智能体能做什么、如何调用——相当于“名片 + 接口文档”
  • 任务（Task）：一个可委派的工作单元及其生命周期（提交 / 进行中 / 完成 / 失败）
  • 消息与产物（Message / Artifact）：协作过程中的沟通内容与最终交付物
MCP 与 A2A 的分工（一句话记住）

MCP 管“我要用工具”，A2A 管“我要找同事帮忙”。

前者是纵向的能力扩展（接入更多外部能力），后者是横向的协作扩展（把任务交给更专业的智能体）。两者是互补而不是竞争关系。

什么时候需要 A2A

当一个任务的完成需要跨越组织边界或系统边界——例如企业内部不同部门的系统、不同厂商的服务。

什么时候不需要

如果所有能力都在自己的代码里，用 MCP 或直接写函数调用就够了——引入跨智能体协议只会增加复杂度。

⚠ 实例层提醒

这类协议仍处在快速演进阶段，名称与规范可能变化。

考试只要求说清『各解决什么问题、二者如何分工』，不要求记具体字段。

可观测性：Agent 迭代的基础设施（考点）环节二 · 知识点讲解 · 考点
要记录六项
  1. ① 模型版本与提示版本
  2. ② 每一步的 Thought / Action / 参数
  3. ③ Observation（工具返回的原始内容）
  4. ④ 耗时与 token 消耗（定位成本热点）
  5. ⑤ 错误与重试
  6. ⑥ 最终输出与用户反馈
三项能力
  • 轨迹（Trace）：把一次完整任务的全过程串起来看——哪一步开始跑偏一目了然
  • 回放（Replay）：用同样的输入重跑，判断问题是偶发还是稳定复现
  • 聚合分析：统计哪类工具最容易失败、哪一步最耗时、失败集中在什么类型的任务上
为什么它对 Agent 尤其重要

单次 LLM 调用输入输出都很短，看一眼就知道问题在哪；而 Agent 一次任务可能有 10–50 步、几十次工具调用、上万 token 的中间内容——没有轨迹，你连“它在哪一步错了”都无法回答，更不用说改进。

所以：先有可观测性，再谈优化。这是 Agent 工程的第一条纪律。

共同启示

Agent 基准普遍比选择题难得多，分数也低得多——这恰恰说明它们更接近真实价值。

对课程项目的启示

你的项目也应该建一个类似的真实任务测试集：不是“问几个问题看回答好不好”，而是一批带明确成功判据的任务（能否跑通、能否查出正确结果、能否生成合规格式）。

然后统计端到端成功率与平均步数——这两个数字最能说明 Agent 系统的实际水平。

安全与权限：Agent 的四条底线（考点）环节二 · 知识点讲解 · 考点
①最小权限

只给完成任务必需的最小权限——查天气不需要读邮件，写周报不需要转账权限。

危害的上限由权限决定，而不是由提示决定（第 14 讲的结论在 Agent 上更加成立，因为 Agent 真的能动手）。

②读写分离

默认只读；写操作必须显式授权。

写操作优先在沙箱或预发环境执行，确认无误后再作用于生产环境。

③不可撤销操作二次确认

下单、退款、转账、发邮件、删数据——必须经人工确认或走审批流程。

并设置额度限制（金额上限、数量上限、频率上限），把“最坏损失”控制在一个可接受的范围。

④全量审计

每一次工具调用都记录参数、结果、时间与发起者，可追溯、可回放。

补充：写操作要有幂等设计——避免重试造成重复下单、重复发信。

一句总结：Agent 的安全不是“让它不做坏事”，而是“让它即使被误导也做不成坏事”——这是系统设计问题，不是提示词问题。
东北大学软件学院 · 自然语言处理22
成本与延迟控制：步数 × 每步成本环节二 · 知识点讲解
Agent 成本的基本公式

总成本 ≈ 步数 × 每步成本　（每步成本 ≈ 输入 token + 输出 token + 工具调用费用）

路线 ① 减少步数
  • 把目标与判据写清楚——减少无效试错（对应失败模式④）
  • 精简工具集——工具越多越容易选错、越容易多试几轮
  • 用更强的模型做规划——一次规划对，胜过反复试错
  • 把确定性任务改写成代码流程，不让模型决定
路线 ② 降低每步成本
  • 分级用模型：简单步骤（生成工具参数、摘要结果）交给小模型
  • 控制上下文长度：截断与摘要工具返回（对应失败模式⑤）
  • 缓存重复的查询结果（语义缓存，第 15 讲）
  • 用量化或小模型做本地步骤（第 15 讲）
延迟的特点

Agent 的延迟是各步之和，所以『并行化无依赖的步骤』是最有效的优化（如同时查三个数据源）。

同时要给过程反馈（“正在查询…已完成 3/5 步”），否则长等待会被用户认为是卡死。

一条务实的原则

能用确定性代码做对的事，就不要交给模型决定。

把模型用在真正需要判断的地方（理解意图、选择工具、处理异常），其余部分用普通程序实现——这是把 Agent 做稳、做便宜最有效的一招。

前沿 ①：多模态大模型环节二 · 知识点讲解 · 前沿巡礼
核心思想：把不同模态都变成“词”
图像 → 切成固定大小的块（patch） → 每块当作一个“词”送进 Transformer 文本 → 分词成 token 序列 两者用同一个注意力机制交互 → “生成某个词时看图像的哪个区域”成为可学习的

  • 统一表示：不同模态最终都变成向量序列
  • 跨模态对齐：注意力负责建立模态之间的对应关系（第 10 讲的软对齐又一次出现）
  • 典型能力：图像描述、视觉问答、图文检索、文档理解（OCR + 版面分析）、视频理解
对学院方向的意义

智慧健康：医学影像 + 报告文本的联合理解（“这张片子对应的报告怎么说”）；金融科技：图表 + 研报文字的联合分析（“这个图表支撑了文中哪个结论”）。

这些都是跨模态对齐的直接应用场景——而它背后的机制，就是第 10、11 讲学的注意力。所以本课程的地基知识在这里依然成立。

前沿 ②：推理模型与长思维链环节二 · 知识点讲解 · 前沿巡礼
核心变化

在回答前进行更长的思考——把思维链从『提示触发的技巧』变成『模型训练出来的默认行为』。

两条技术路径

① 用强化学习激励推理：在答案可自动验证的任务（数学、代码）上用 GRPO 等算法训练，让模型自己探索出更长的解题链（第 13 讲）。

② 在推理阶段投入更多计算（test-time compute）：采样多个候选、搜索、自我验证、投票（第 14 讲）。

两者可以叠加：训练时让它学会想，推理时让它多想。

三条必须说清的边界
  • 成本与延迟显著上升——思考的 token 也要付费与等待
  • 简单任务上收益很小甚至为负——想太多反而出错，且浪费成本
  • 长思考链依然不忠实——第 14 讲的判断依然成立，仍需要外部验证
一个实用判断

不要对所有任务都用“最高推理档位”。按任务难度分流：简单问答、格式转换、抽取类任务用普通模式（快而便宜）；数学、复杂推理、代码调试用深度思考模式（慢而准）。

这与第 14 讲『CoT 的收益高度依赖任务类型』是同一个判断，只是现在这个判断从提示工程层上升到了模型选择层。

这也是软件工程专业学生的机会所在——模型能力是共同的，而流程设计与工程落地是你们的主场。

前沿 ⑤：合成数据与自我改进（考点）环节二 · 知识点讲解 · 前沿巡礼
三种用法

① 生成指令数据：用强模型批量生成指令-回答对，再人工或自动筛选（第 12 讲 self-instruct 的思路）。

② 生成推理过程：为数学题生成解题链，用于训练推理能力（第 13 讲）。

③ 自我博弈与自我改进：模型生成候选 → 验证器筛选 → 用筛选结果训练自己。

三个必须讲清的风险
  • 模型退化：反复用自己生成的数据训自己，分布尾部逐渐丢失，多样性与质量一起下降
  • 偏差放大：教师模型的错误与偏见被固化进下一代模型
  • 评测污染：生成的评测数据可能无意中与真实评测集高度相似，导致分数虚高
工程上的稳健做法

① 保留人类数据作为锚点——完全脱离人类数据的自我循环风险最高；
② 用验证器筛掉低质样本（可执行结果、规则校验、另一模型打分）；
③ 监控多样性指标而不只看分数——分数上升但输出越来越同质，是退化的早期信号。

一句话：合成数据是放大器，不是替代品。

呼应第 13 讲的『数据墙』：当人类文本不够用，合成数据是必然方向，但它的第一原则是“别把模型喂退化”。

四条主线：比按章节记更有效课程收口 · 复习索引
①表示：文本如何变成机器能算的东西

one-hot → 词向量（第 5 讲）→ 上下文化表示（第 6、12 讲）→ 子词（第 4 讲）→ 向量检索（第 15 讲）。

核心问题始终是：怎么让语义相近的东西在数值上也相近。

②建模：如何在变长序列上做预测

规则 → 计数（N-gram，第 7 讲）→ 循环（RNN/LSTM，第 8 讲）→ 注意力（第 10–11 讲）→ 预训练 + 微调（第 12–13 讲）。

每一代都在解决上一代的具体缺陷：稀疏、长程、串行、标注依赖。

③评估：怎么知道做得好不好

准确率 / 精确率召回率 → 困惑度（第 7 讲）→ BLEU（第 10 讲）→ 实体级 F1（第 9 讲）→ 多指标 + AI 评委 + 人工校准（第 14–15 讲）。

贯穿始终的两条纪律：指标要匹配任务；口径要写清、要可复现。

④工程：怎么把它做成可用的系统

成本与延迟（第 13、15 讲）· 可靠性与可观测性（第 16 讲）· 权限与合规（第 14、16 讲）· 评估与迭代（第 14、15 讲）。

这条主线在期末考试里占比不高，但在你的职业生涯里占比最高。

建议：复习时按四条主线各梳理一遍，比按 16 讲逐章背更有效——因为主线才是可迁移的能力。

期末项目评分细则（共 45%）课程收口 · 考点
评分项占比评什么拿分要点
① 提案5%选题价值、技术路线、分工与里程碑问题定义清楚、技术路线有依据、分工到人、里程碑可检查
② 中期检查5%进度、demo 截图、风险与对策有可演示的最小版本；风险要写出来并给出对策
③ 实现与报告25%代码质量、功能完整度、技术深度、报告规范性、可复现性能跑通；有评估数据；有参数对比实验；报告含环境说明与种子；有 AI 使用声明
④ 答辩10%表达清晰、回答追问、说明取舍与不足讲清“为什么这么设计”；能说出哪里没做好、下一步怎么改
两条硬门槛

① 可运行——不能跑通的系统，写得再好也不及格。答辩前务必在一台“干净”的机器上验证一次。

② 可复现——环境说明、随机种子、超参记录、评估脚本、提示版本、模型版本，缺一不可。

技术深度从哪体现

不是“用了多大的模型”，而是：① 做了参数对比实验并给出结论；② 定位了瓶颈并解释原因；③ 对失败做了归类分析；④ 说清了技术选型的取舍理由。

一个用 7B 模型 + 完整评估 + 诚实分析的项目，得分会高于一个用 70B 模型但只有一个分数的项目。

期末报告的建议结构（八节）课程收口 · 写作指南
前四节：说清“做了什么”

① 问题定义与背景：解决什么问题？给谁用？成功判据是什么？

② 相关工作与方案选型：为什么选这个方案？对比了哪些替代方案？

③ 系统设计：架构图、模块划分、数据流。

④ 实现细节：关键技术点、遇到的具体问题与解决方式——这部分最能体现工作量。

后四节：说清“做得怎么样、边界在哪”

⑤ 评估：指标、测试集、结果表、与基线的对比。

⑥ 错误分析与局限：哪类样本失败？为什么？下一步怎么改？

⑦ 工程与伦理：成本、延迟、权限、隐私、AI 使用声明。

⑧ 分工与贡献：每人具体做了什么（避免“大家都做了一点”）。

拉开分差的地方

第⑤、⑥两节。只有结果表、没有错误分析与局限讨论的报告，通常拿不到高分——因为老师无法判断你是“真的理解了系统”还是“碰巧跑出了一个数字”。而一个能说清“我的系统在什么情况下会失败、为什么”的团队，显然对技术有更深的掌握。

答辩要求与常见追问课程收口 · 8 分钟陈述 + 5 分钟提问
陈述的四段结构（8 分钟）

① 问题与目标（1′）：解决什么问题、给谁用、成功判据是什么。

② 系统演示（3′）：现场跑一遍真实用例，并展示至少一个「难例」。

③ 技术与评估（2.5′）：架构选择的理由、评估结果、与基线的对比。

④ 局限与下一步（1.5′）：坦诚说出不足与改进方向。

演示不要只放截图——现场跑通比任何幻灯片都有说服力；同时准备录屏兜底（网络、限流、数据都可能出问题）。

四类常见追问
  • 为什么不用微调 / 为什么不用 RAG？（考察选型依据）
  • 评估集怎么建的？有没有和训练数据重叠？（考察评测严谨性）
  • 失败最多的是哪类样本？为什么？（考察是否有真正的错误分析）
  • 成本与延迟是多少？（考察工程意识）
两个加分点与一个减分点

加分：① 主动说出局限与失败案例——这说明你真的测过、想过；② 展示参数对比实验与瓶颈定位过程。

减分：把功劳都归给“我们用了某某大模型”，却说不出为什么选它、它在哪里失败、成本是多少——这会被判定为缺少工程判断力。

研讨：三个问题（10 分钟）环节三 · 研讨 · 答案课堂揭示
Q1为什么 Agent 的可靠性更难保证？

一次 LLM 调用错了可以重试，为什么 Agent 错了可能无法挽回？请从“动作空间”说起。

提示：多步串联的误差累积；行动不可撤销；行为不确定、失败难以穷举测试。

Q2为什么“最小权限”是安全底线？

提示注入的防御为什么不能只靠“写好提示词”？“危害的上限由什么决定？”

提示：即使模型被误导，它能造成的最大破坏由什么决定？只读与写权限的差别有多大？

Q3答辩时应该主动展示什么？

同样的系统，两支队伍的答辩得分可能差别很大。哪些内容能体现真正的工程判断力？

提示：局限与失败案例；选型依据；参数对比实验；成本与延迟。

本讲小结 · 5 分钟
一个定义、一条纪律、一条底线。
  • 一个定义：Agent = 模型 + 工具 + 记忆 + 规划

课程总结：从文本到智能课程收口
十六讲的主线

表示（让机器能算）→ 建模（让机器会预测）→ 架构（让机器并行看全句）→ 预训练（让机器吃掉互联网）→ 对齐（让机器听懂人话）→ 工程（跑得便宜 · 答得准 · 用得负责）

你真正学到的

不是模型名字，而是四条可迁移的主线：

① 表示：怎么让语义相近的东西在数值上也相近。
② 建模：怎么在变长序列上做预测。
③ 评估：怎么用合适的指标判断好坏。
④ 工程：怎么把方法做成可用的系统。

给学生的三点建议

① 遇到新模型先问三件事：它属于哪一条路线？训练目标是什么？上下文多长？——这能过滤掉大部分营销噪音。

② 任何结论都要有评估支撑，包括你自己的实验——“我觉得效果变好了”不是结论，“准确率从 78% 提到 84%，测试集 100 条”才是。

最重要的一条职业素养

永远对模型输出保持验证意识。

因为流畅不等于正确，自信不等于可靠，引用不等于支持。

这门课教你的技术会过时，但这条判断力会一直有用——尤其当你要为别人的决策负责时。

叮嘱 ① 不要删失败案例

不要为了“好看”而删掉不成功的实验。诚实的错误分析是加分项——它证明你测过、想过、理解边界在哪。

叮嘱 ② 提前验证可复现性

不要在最后一天才去干净机器上跑一遍。环境与依赖问题是答辩当天最常见的翻车原因。

叮嘱 ③ 把没做完的写进计划

如果还有想做的事没做完，把它写进『下一步计划』，而不是硬塞进系统。说清边界比假装完备更专业。
