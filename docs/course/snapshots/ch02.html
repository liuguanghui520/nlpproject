正则表达式是什么？环节二 · 知识点
定义

一种用“模式（pattern）”描述一类字符串的形式语言：把“想找什么”写成机器可执行的规则。

五种用途

检索（有没有）、提取（找出来）、校验（合不合法）、替换（改掉）、切分（断开）。

一个类比

文本世界的“寻人启事”——不必说出具体是谁，只凭特征就能把一类人找出来。

想找 woodchuck 与 woodchucks 两种写法 → 一条模式搞定： woodchucks? # s? 表示 s 可有可无
正则不是“查字典”，而是描述一类字符串的语言。

正则的六个真实战场环节二 · 知识点

五件套①：字符类与取反环节二 · 知识点
模式含义例子
[wW]oodchuck方括号：其中任意一个字符匹配 Woodchuck 与 woodchuck
[a-z]范围：一个连续区间匹配任意一个小写字母
[0-9]范围：数字“Chapter 1” 中的 1
[A-Za-z0-9_]多个区间可合并Python 变量名允许的字符
[^Ss]取反：不是 S 也不是 s“I have no exquisite reason” 中的其他字符
[^e^]^ 只在最前表示取反匹配除 e 与 ^ 之外的字符
一句话：[] 表示“任意一个”，^ 放最前表示“除这些之外”；中文常用 [\u4e00-\u9fff]。
东北大学软件学院 · 自然语言处理10
五件套②：量词环节二 · 知识点
模式量词含义能匹配
colou?r?：0 或 1 次color、colour
oo*h!*：0 次及以上oh!、ooh!、oooh!、ooooh!
o+h!+：1 次及以上ooh!、oooh!（不含 oh!）
baa{3}{n}：恰好 n 次baaa（b 后跟 3 个 a）
ba{2,4}{n,m}：n 到 m 次baa、baaa、baaaa
默认贪婪：能多匹配就不少匹配；在量词后加 ? 可改为懒惰——第 13 页展开。

五件套③：锚点与边界环节二 · 知识点
模式含义例子
^行首^[A-Z]：以大写字母开头的行
$行尾\.$：以句号结尾的行
\b词边界\bwood\b 只匹配独立的 wood，不匹配 hardwood
\B非词边界\Bwood 匹配 hardwood 中的 wood
re.findall(r'\bwood\b', 'hardwood wood wooden') # → ['wood'] ← 边界把误报挡在门外
锚点匹配的是位置而非字符——它让模式的“落点”更准。
东北大学软件学院 · 自然语言处理12
五件套④：分组、或与贪婪环节二 · 知识点
1或与捕获组
  • groundhog|woodchuck：二选一
  • (wood)?chucks：整体可选
  • 捕获组会“记下”内容，用 m.group(1) 取出
2非捕获与回引
  • (?:...)：只分组、不捕获
  • (\w+)\s+\1：找连续重复词（the the）
  • 回引是文本质检的经典手段
3贪婪 vs 懒惰
  • <b>.*</b>：贪婪，整段吞掉
  • <b>.*?</b>：懒惰，逐段匹配
  • 一对多标签的场合，懒惰几乎总是对的
分组让正则从“匹配”升级为结构化提取——这是正则与业务结合的关键一步。

五件套⑤：速记符与转义环节二 · 知识点
模式含义等价写法 / 注意
\d任意数字[0-9]
\w词字符Python 3 默认匹配 Unicode 词字符（含中文），加 re.ASCII 才回到 [A-Za-z0-9_]
\s空白字符空格、Tab、换行等
\D \W \S取反非数字 / 非词字符 / 非空白

零宽断言：只判断位置，不消耗字符环节二 · 知识点
模式含义例子
(?=...)前瞻：后面必须跟…Windows(?=95|98) 只匹配后接 95/98 的 Windows
(?!...)负前瞻：后面不能跟…foo(?!bar) 匹配后面不是 bar 的 foo
(?<=...)后顾：前面必须是…(?<=\$)\d+ 只取 $ 后面的数字（$ 不参与匹配）
(?<!...)负后顾：前面不能是…(?<!\d)\d{11}(?!\d) 电话前后不粘连数字
断言匹配的是“位置”而不是字符——密码校验与边界控制的两大利器。

Python re 模块：六大函数环节二 · 知识点
函数作用
re.search(p, s)返回第一个匹配对象
re.match(p, s)只从开头匹配
re.findall(p, s)返回所有匹配的列表
re.finditer(p, s)返回迭代器（省内存）
re.sub(p, r, s)替换所有匹配
re.split(p, s)按模式切分
re.compile(p)预编译，复用更高效
写法要点
  • 模式统一写进 r'' 原始字符串，反斜杠不打架
  • 标志位：re.I 忽略大小写、re.M 多行、re.S 点号匹配换行
  • 有分组时 findall 返回元组列表
re.findall(r'\d+', '电话 207-587-3290') # → ['207', '587', '3290']
复杂模式先 compile 再复用；想替换时 sub 最趁手。

实战①：提取邮箱地址环节二 · 知识点
# 第一步：基础可用版本 pattern = r'[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}' re.findall(pattern, text)
它做对了什么

能抓住绝大多数常规邮箱：guogb@swc.neu.edu.cn、a.b+c@example.com。

会误报（FP）

句尾句号会被吞进去：mail@x.com. 多带一个点；连续符号也可能放行。

会漏报（FN）

新顶级域 .ai/.io 可能漏；中文邮箱、Unicode 域名也不在模式内。

一个“完美”邮箱正则可能有上百字符——工程上先定精度目标，再写模式。

实战②：提取电话号码环节二 · 知识点
同一条信息三种写法：207-587-3290　5583446854　(207) 107-929——模式要能都接住。
# 括号可选 → 分隔符可选（- . 或空格）→ 三段数字 pattern = r'\(?\d{3}\)?[-.\s]?\d{3}[-.\s]?\d{4}' # 用分组统一格式：207-587-3290 → (207) 587-3290 re.sub(r'(\d{3})-(\d{3})-(\d{4})', r'(\1) \2-\3', s)
渐进式写法

先写只支持“-”的最简版，再逐项加 ? 兼容括号与空格，边加边测。

工程价值

很多清洗任务的目标不是“提取”，而是统一格式——为后续入库、检索服务。

先枚举格式、再统一格式——“统一”比“完美提取”更实用。

实战③：网页文本清洗三件套环节二 · 知识点
从“源码”到“干净正文”，三步、三行正则：
import re, html clean = re.sub(r'<[^>]+>', '', raw) # ① 去标签 clean = html.unescape(clean) # ② 解实体 &nbsp; → 空格 clean = re.sub(r'\s+', ' ', clean).strip() # ③ 压缩空白
为什么这样写

[^>]+ 避免 .*? 的嵌套问题；每步只解决一类噪声，可单测。

还能再加

删脚本样式：<script>.*?</script>（配 re.S）；去掉多余空行。

与大模型分工

规则确定的结构噪声交给正则；语义模糊的改写润色交给大模型（第 14 讲）。

清洗三件套：去标签 → 解实体 → 压空白——每步一条正则，可测试、可复用。
东北大学软件学院 · 自然语言处理18
案例：敏感信息脱敏环节二 · 知识点
text = "张三 210101199001011234 13812345678 6222021234567890" text = re.sub(r'\d{17}[\dXx]', '[ID]', text) # 身份证 text = re.sub(r'1[3-9]\d{9}', '[PHONE]', text) # 手机号 text = re.sub(r'\d{16,19}', '[CARD]', text) # 银行卡 # → 张三 [ID] [PHONE] [CARD]
三个要点
  • ① 先规范化再脱敏：全角数字先 NFKC 归一，否则漏脱
  • ② 保留格式线索（如 138****5678）比整段删除更利于分析
  • ③ 日志与语料入库前必须过这一关——合规红线
脱敏不是“抹掉”，而是在合规与可用之间留好线索——先规范化、再替换。
东北大学软件学院 · 自然语言处理19
案例：日期时间归一化环节二 · 知识点
text = "会议：2026/9/10 与 2026-09-10 及 2026年9月10日" pat = re.compile(r'(\d{4})[/年-](\d{1,2})[/月-](\d{1,2})日?') def norm(m): return f"{m.group(1)}-{int(m.group(2)):02d}-{int(m.group(3)):02d}" pat.sub(norm, text) # → 会议：2026-09-10 与 2026-09-10 及 2026-09-10
标准套路
  • 分组捕获年 / 月 / 日 → 回引重组统一格式
  • 日期、电话、编号、价格通用同一套路
  • 正则管形状，范围校验管合法性（月 1–12、日 1–31）
“统一格式”比“完美提取”更实用——分组捕获 + 回引重组是归一化的标准套路。

误报与漏报：正则的质量观环节二 · 知识点
FP误报（False Positive）

匹配了不该匹配的——邮箱模式把句尾句号也吞了进来；统计上对应 Type I 错误。

FN漏报（False Negative）

该匹配的没匹配——+86 139… 这种带区号的号码被漏掉；对应 Type II 错误。

先问代价

二者往往此消彼长：放宽模式 → 漏报降、误报升。动手前先想清楚哪个代价更大。

正则没有“对错”，只有误报与漏报——写完模式先自问：我会错抓什么？会漏什么？
东北大学软件学院 · 自然语言处理19
精确率与召回率：把质量变成数字环节二 · 知识点
P精确率 Precision
  • P = TP ÷ (TP + FP)
  • 问题：抓到的里面，有多少是对的？
  • 高精确场景：表单校验——宁可放过，别误伤合法用户
R召回率 Recall
  • R = TP ÷ (TP + FN)
  • 问题：该抓的，抓到了多少？
  • 高召回场景：PII 脱敏——宁可误杀，不可放过一个身份证号
算一遍 + F1
  • 找出 20 个“手机号”：18 真 2 假，另有 5 个真号漏抓
  • P = 18/20 = 90%；R = 18/23 ≈ 78%
  • F1 = 2·P·R ÷ (P+R)：调和平均，综合评价两端
精确率与召回率是贯穿全课程的评估语言——第 10 讲 BLEU、第 15 讲 RAG 评估与此同源。

规范化①：大小写折叠环节二 · 知识点
为什么折叠

把 Apple / apple / APPLE 归并为同一表示，减小词表、提高统计覆盖——这是检索系统的经典第一步。

怎么做

"HELLO".lower() → "hello"；先判断任务：情感、专名、缩写的场景可能要保留原样。

语言坑

德语 ß → ss；土耳其语 ı 与 i 不是一回事；简单 lower 并不“通用”。

折叠前先问任务：归并是为了算得动，不是无脑变小写——全大写 APPLE 可能自带情绪。

规范化②：词形还原 vs 词干提取环节二 · 知识点
维度词形还原（Lemma）词干提取（Stem）
做法词典 + 词性，还原到规范词形规则砍后缀，不看词典

中文文本预处理环节二 · 知识点
1全半角统一（NFKC）

１２３ → 123，￥ → ¥；一行 unicodedata.normalize('NFKC', s) 即可归一全半角与兼容字符。

2繁简转换

繁体 → 简体，常用 OpenCC；语料来源混合时先统一再统计。

3噪声清洗

去表情/颜文字、URL、@用户、连续标点；正则按字符范围写 [\u4e00-\u9fff]。

4词的边界

中文没有空格，“词”要靠分词确定——这是第 4 讲《分词与子词》的主角。

5隐私脱敏

身份证、手机号、病历等敏感信息必须先脱敏再处理，遵守个人信息保护要求。

6编码统一

统一 UTF-8、读写显式 encoding='utf-8'；“锟斤拷”多为 GBK/UTF-8 混用，乱码可用 ftfy 修复。

中文没有空格：清洗与分词往往一起做——这是第 4 讲的伏笔，也是国产模型中文数据的起点。

字符集与编码：乱码的正解环节二 · 知识点
编码特点例子现状
ASCII7 位，仅 128 个字符'A' → 0x41子集，兼容保留
GBK中文双字节，兼容 ASCII'中' → 0xD6D0历史中文系统常见

四个高频易错点环节二 · 知识点
1贪婪陷阱

.* 会把一对多标签整段吞掉；优先用 .*? 或 [^...]* 把匹配限制在段内。

2match vs search

re.match 只从字符串开头匹配，“明明有却找不到”多半是这个原因。

3忘记转义

. 匹配任意字符；真正的句号要写 \.；正则里的“原样字符”常需要反斜杠。

4正则过拟合

为样例写出的巨长模式，换一批文本就全失效——先定义任务与边界，再写模式。

能解释自己正则会错抓什么、会漏什么，才算真正会写。

正则的边界：什么时候不该用环节二 · 知识点
场合为什么不用正则交给谁
解析 HTML / XML嵌套结构，正则等价有限自动机做不了递归BeautifulSoup / lxml
解析 JSON / CSV转义与嵌套规则复杂，手写易错json / csv 标准库

正则的工程化写法环节二 · 知识点
三个维护性技巧
  • re.X 详细模式：忽略空白、支持 # 注释，长模式拆成多行
  • 命名分组：(?P<name>...) 用 m.group('name') 取值，不靠数字编号
  • 预编译：re.compile 一次解析，循环里反复复用
pat = re.compile(r""" (?P<area>\(?\d{3}\)?) # 区号，括号可选 (?P<sep>[-.\s]?) # 分隔符可选 (?P<num>\d{3}[-.\s]?\d{4}) # 号码主体 """, re.X) for line in texts: m = pat.search(line) if m: print(m.group('area'), m.group('num'))
单次匹配无所谓，批量处理时可读性 + 预编译就是性能与可维护性本身。

正则安全：ReDoS 灾难性回溯环节二 · 知识点
灾难现场
  • 模式 (a+)+$ 匹配 aaaaaaaaaaX：内外量词组合方式指数爆炸
  • 30 个 a 加一个 X，就可能让一次匹配耗尽 CPU
  • 被用于拒绝服务攻击，就叫 ReDoS——生产事故级风险
防御三招
  • ① 消灭嵌套量词：(a+)+ 这类写法直接重写
  • ② 原子组 (?>...) / 占有量词 ++：禁止回溯
  • ③ 限制输入长度 + 设置匹配超时（re 第三方实现 / regex 模块）
正则不是安全无害的——写进生产代码前，先问这个模式会不会被恶意输入拖垮。
东北大学软件学院 · 自然语言处理23
性能：预编译与占有量词环节二 · 知识点
三种量词逐字对比
  • 贪婪 .*：先吞多、必要时吐回
  • 懒惰 .*?：先吞少、不行再加
  • 占有 .*+：吞了不吐，禁止回溯；原子组 (?>...) 同效
两条性能铁律
  • ① 循环里用 compile，解析只做一次
  • ② 能用字符类限定范围（[^>]*）就别用 .*
  • 例：(a|ab)c 匹配 abc 需回溯，(?>a|ab)c 不回头
性能第一原则：少回溯——占有量词与原子组是 ReDoS 防御的第一道闸。

正则 + 大模型：混合抽取流水线环节二 · 知识点
分工：规则粗筛 + 模型精判
  • 正则：先扫出电话 / 邮箱 / 日期等高确定性字段，秒级、零成本
  • LLM：对疑似片段做归属判断与规范化，处理格式变体

  • ② LLM 精判：哪段经历属于哪家公司、时间与职位对齐
  • ③ 输出 JSON，正则校验字段齐全后入库
不是二选一，而是分工：规则层兜底、模型层提精度——第 15/16 讲 RAG / Agent 里还会再见。
